# Rule pack — draft schema

**Status: draft.** 2026-08-11.

The ~200 rules from `Dasturhāye Vāžesāzi az Kārbonhā.docx` as data. YAML in git
is the source of truth; a loader syncs it into Postgres.

## Rule numbering

**We define our own numbering. Everything in the project refers to it.**

The source document numbers rows per table, so "rule 10" is ambiguous — there
is a rule 10 in the verb table and another in the nominal table. karbon has a
third, unrelated scheme (see [LEXICON_ANALYSIS.md](LEXICON_ANALYSIS.md)). One
canonical id ends that.

### Format

`FAMILY-NNN`

| Family | Meaning | Range |
|---|---|---|
| `S` | stem rules: infinitive → kārbon-e do | S-01 … S-09 |
| `V` | derivation from a verb stem | V-001 … V-082 |
| `N` | derivation from a noun, adjective, adverb or pronoun | N-001 … N-105 |
| `G` | glide rules | G-01 … G-17 |

Compounding templates are not a separate family — they live in `V` and `N`
with `kind: template`, because that is where the source document puts them.

**There is no `D` family.** An earlier draft of this document planned one:
"D-001 … D-004, the 4 rules that make a verb from a noun/adjective", in a
`verbalisers.yaml`. No such group exists. All 19 documents in the Drive archive
and the earlier prototype at `~/Code/mosaic/murfulu` were searched on
2026-08-11 and none defines it. `Konzept/درآمد_پروژه.docx` names exactly **two**
such rules — `-idan` for the intransitive (*rowšan* → *rowšanidan*, to become
bright) and `-āndan` for the transitive (*rowšanāndan*, to make bright) — and
those are verb-table rows 3 and 4. Verb-table rows 1 and 2 also produce
infinitives, but from a verb stem, so they are causatives and belong with the
other deverbal rules.

So the two denominal rules are **V-003 and V-004**, carrying a
`makes_verb_from_nominal` flag so they can still be listed together. No `D` id
was ever issued, and none ever will be. The reason is kept in
`rules/rule_ids.json` under `retired_families`.

This follows the same principle the family table already applies to compounding
templates: a rule belongs to the family of the table it comes from.

Stem exceptions are data attached to a stem rule, not rules themselves. They
are addressed as `S-09/raftan`.

### The three unbreakable rules

1. **An id is permanent.** Once assigned it never changes meaning and is never
   reused.
2. **New rules are appended**, never inserted. A new verb rule becomes V-082,
   even if it logically belongs beside V-010.
3. **Nothing is deleted.** A retired rule keeps its id and gets
   `active: false`, so old references, stored derivations and expert feedback
   still resolve.

Ordering for display is a separate `sort_key` field. Never reorder by
renumbering.

### The register

`rules/rule_ids.json` is the permanent record: one entry per source row, with
the id and the row it came from. Generated by `tools/assign_rule_ids.py`, which
refuses to write a register that would move an existing id to a different row.

All four families are assigned, from two transcriptions —
`rules/source_rows.json` (the word-formation grammar) and
`rules/stem_source_rows.json` (the stem-rules file):

| Family | Ids | From |
|---|---|---|
| `V` | V-001 … V-082 | verb table rows 1–81, plus one unnumbered row |
| `N` | N-001 … N-105 | nominal table rows 1–104, plus one unnumbered row |
| `G` | G-01 … G-17 | glide table, document order |
| `S` | S-01 … S-09 | stem rules 1–9 |

The stem rules number the same way: `S-04` is stem rule 4. The document's two
sub-rules, which it writes as 4-1 and 4-2, are **parts of S-04**, not rules of
their own — the text says stem 2 divides into "eight groups", which is rules
2–9. The 39 exception verbs are data attached to their rule, addressed as
`S-09/raftan`.

Three things the source document forced, all mechanical:

- **The number in a V or N id is the document's own row number.** That is what
  makes `source: {table, row}` redundant but readable, and it is what the
  worked examples below assume.
- **V-077 is reserved and never used.** Verb-table row 77 is blank in the
  source. The id is recorded with its reason so nothing later fills the gap.
- **The unnumbered rows are appended, not inserted.** Each rule table has one
  row the document forgot to number: `-gi` on a `karidekarbahr` ending in `-e`
  (after row 8) and `-vand (Nesbat)` (after row 84). They become V-082 and
  N-105, at the end of their family, with `follows_row` recording where they
  sit in the document.

The glide table is the exception to the row-number rule: it numbers its own
header row "1", so its numbers are offset by one from its rules. G ids follow
document order instead.

Three exception rows could not be read cleanly and are flagged
`needs_expert_check` rather than repaired: گشادن (the document says "as rule 4"
instead of giving stems), افراشتن (three forms given where two are expected)
and نهفتن (the document writes ؟ for the second stem).

### Traceability

Every rule keeps both:

```yaml
id: V-010                              # ours — canonical, used everywhere
source: {table: verb_stems, row: 10}   # the original document row
```

karbon's `stem_rule` number is stored on lexicon entries as
`karbon_stem_rule`, clearly labelled, **never used for logic** and never shown
without saying it is karbon's.

### Versioning

The rule pack carries a semantic version. Adding a rule or changing a
`strength` is a minor bump. Changing what a rule *does* is a minor bump with a
changelog entry naming the id. Removing is not a thing — only deactivating.

Every stored derivation records the rule-pack version that produced it.

### Published in the app

The Rules screen is the canonical published reference — every rule, in
Persian, with its id, affix, input and output type, semantic tag, examples,
authored strength and measured productivity. Every rule id shown anywhere in
the app links to it, and the API exposes `/rules/{id}` so an id is a stable
address the linguist can send in a message.

## Files

```
rules/
  source_rows.json        verbatim transcription of the grammar's tables
  stem_source_rows.json   verbatim transcription of the stem rules
  rule_ids.json           the permanent id register
  lexicon_categories.yaml lexicon category → word class
  semantic_tags.yaml      the closed tag set with gloss templates
  verb_stems.yaml         82 rules from kārbon 1 and 2
  nominals.yaml           105 rules from nām, barnām, čonvāže, jānām
  glides.yaml             17 vowel-meeting rules
  stem_rules.yaml         9 rules, infinitive → kārbon-e do, with exceptions
```

Split by source table, so each file maps to one table of a source document and
a rule can be traced back to its row. There is no `verbalisers.yaml` — see the
note on the retired `D` family above.

## Rule shapes

Three kinds cover everything in the tables.

### Suffix / prefix

```yaml
- id: V-010
  source: {table: verb_stems, row: 10}
  kind: suffix
  affix: "-ār"
  input:
    type: karbon_yek
    condition_text: "mostly with final -t or -d"
    condition_regex: "[td]$"
    strength: typical            # see below
  output:
    type: karnam
  semantics: null
  examples: ["goft + ār = Goftār"]
  label_fa: "کاربن یک + ār-"
  explanation_fa: "از کاربن یک با پسوند ār- کارنام ساخته می‌شود"
  active: true
```

**Every rule carries Farsi text.** The interface is in Farsi and the engine
cannot invent it, so `label_fa` and `explanation_fa` are required fields — as
are `gloss_fa` on semantic tags and an explanation on each glide rule.

```yaml
- id: V-053
  source: {table: verb_stems, row: 53}
  kind: prefix
  affix: "bar-"
  input:  {type: nabesudkarvaze, strength: obligatory}
  output: {type: nabesudkarvaze}
  semantics: {tag: bala}         # "up"
  examples: ["barangixtan", "barnešastan"]
  active: true
```

### Template (compounds)

Rows like *Kārbon-e yek + o + Kārbon-e yek of another verb* → *Zadoxord*.

```yaml
- id: V-017
  source: {table: verb_stems, row: 17}
  kind: template
  pattern: "{a} + o + {b}"
  slots:
    - {name: a, type: karbon_yek}
    - {name: b, type: karbon_yek, constraint: different_verb}
  output: {type: karnam}
  examples: ["Zadoxord", "Goftošenid"]
  active: true
```

`constraint` values seen in the tables: `same_verb` (*Goftogu*),
`different_verb` (*Zadoxord*), `same_stem` (*Kešākeš*), `negated`
(*Budonabud*).

### Glide

```yaml
- {left: "ā", right: "i", result: "āyi", example: "dānā + i = Dānāyi"}
- {left: "u", right: "e", result: "uye", example: "gu + eš = Guyeš"}
- {left: "ow", right: "a", result: "av", example: "row + am = ravam"}
```

Applied at every join. Not optional — most affixation in the tables triggers
one.

## Type vocabulary

the project's grammar terms, transliterated, used as the machine identifiers:

`karbon_yek` · `karbon_do` · `nabesudkarvaze` · `karnam` · `nam` · `barnam` ·
`karandekarbahr` · `karidekarbahr` · `jonvaze` · `janam` · `pisvaze` · `nedayi`

A rule matches when the input word's type equals `input.type`. Some rules take
an already-derived form (e.g. `-gi` attaches to a `karidekarbahr` ending in
`-e`), which the recursion handles naturally.

## Semantic tags

A closed set, roughly 35 entries, taken from the brackets in the source grammar:
Mānand, Jā, Zamān, Nesbat, Dāštan, Anbuhi, Kučaki, Sezāvāri, Bāni, Āxšij, Nāi,
Badi, Vārun, Vorud, Pasravi, Koneši, Jens, Čoni, Nāmsāz, Pirāmun, …

Each carries a gloss template, so the generated word gets a stated meaning
rather than a guessed one:

```yaml
- tag: ja
  gloss_fa: "جایی که {stem} در آن است"
  gloss_en: "place where {stem} is"
  example: "Namak + dān = Namakdān"
```

This is what turns "here is a form" into "here is a form and what it means".

## Open problem: rule strength

Many rows are tendencies, not rules. Row 10 reads *"kārbon-e yek, **mostly**
with final -t and -d"*. Row 13 lists four affixes together. If we encode these
as hard rules, the engine will over-generate and every output will look equally
confident.

Draft: every rule carries `strength`.

| Value | Meaning | Effect |
|---|---|---|
| `obligatory` | applies whenever the input type matches | full weight |
| `typical` | applies, with a stated tendency | reduced weight |
| `occasional` | attested but rare | flagged, low weight |

`strength` feeds the score directly, and it is a field an expert can set — which
makes it a linguistic judgement, not an engineering guess.

Alternative worth considering: drop `strength` from the YAML entirely and
**measure** it from the corpus instead, as Baayen P per rule. That is more
honest but only works for rules whose outputs are attested; new or rare rules
would have no value at all. A hybrid — the authored `strength` as the prior, corpus
P as the evidence — is probably right.

## Traceability

Every rule keeps `source: {table, row}`. When an expert reviews, we can show him
his own row number. When a generated word looks wrong, we can name the exact
line of the document that produced it.

## What a rule says about its base, beyond the word class

Added 2026-08-12. The source states a condition for **186 of the 195 rules**.
For 164 it repeats the word class, which `input_types` already enforces.
**Twelve say more** — a final letter on the base, or the stem's group — and
nothing was reading them.

`rules/input_conditions.yaml` holds those twelve as an authored table. Each
entry quotes the source line verbatim and a test fails if the quote drifts
from the pack. Ends-with tests are on the **Latin**: Behnevis is phonemic, so
a condition about a final sound is a condition about a final letter, which it
would not be in the script.

**A condition never refuses to build a word.** V-010 hedges with *bištar* —
mostly — and a tendency reported as a prohibition would overstate the grammar.
Whether a failed condition should stop a rule is the linguist's ruling. The
result records `condition_met`, which is **three-valued**: true, false, or
*not established* — the last covering both "this rule states nothing" and
"this rule states something nobody has ruled on yet". See OPEN_QUESTIONS S7.
